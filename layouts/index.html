Image processing in pure Go.
No OpenCV. No libvips.

The scikit-image vocabulary over an RGBA raster — blur, edges, morphology, geometry, colour — with CGO_ENABLED=0, so it cross-compiles to a static binary and runs in a browser tab. Image processing in most languages means binding a C library; this is one portable module, accelerated by go-asmgen SIMD. BSD-3-Clause.

Why it exists

Because the alternative is a C library.

OpenCV and libvips are excellent, and they are C: a cgo build, a system package, a cross-compilation problem, and nothing at all in a browser. go-images is one module that builds for every target Go builds for — and where the work is separable and hot, it is faster than scikit-image rather than merely portable.

🧩

A vocabulary, not a framework

The names are scikit-image's, so somebody porting a pipeline reads one list and recognises it: gaussian_blur, sobel, canny, erode, dilate, resize, otsu.

⚡

SIMD where it pays

Kernels generated by go-asmgen for amd64 (SSE2), arm64 (NEON) and s390x (vector). The portable scalar core is what the other targets run, and the benchmark pages say which is which rather than quoting the best number.

📉

Honest where it loses

It beats scikit-image on box blur and Sobel — the separable hot operations — and the documentation names the operations where it does not, because a benchmark page that only shows wins is an advertisement.

🌐

And in a browser

CGO_ENABLED=0 means GOOS=js works, which is the one thing no binding to a C library can offer: the pictures never leave the machine.

The organisation

One library, three codec forks, two readers.

Each is its own module with its own release line. The three forks of Go's own codecs carry their changes in a NOTICE and pass Go's suite unaltered; a reader registers itself with image.Decode, so a caller imports it for its side effect and never names it again.

The bar

100% of statements, and a judge that is not us.

💯

Coverage is a gate, not a goal

Every repository here fails its own CI below 100% of statements, error branches included. ⛔ And the gate reads the profile rather than the percentage: total: 99.95% prints as 100.0%.

🔬

Validated against scikit-image

The library's filters are compared against the thing it borrows its vocabulary from, which is the only way a claim about a blur means anything: a filter checked against its own output is checked against its author.

⚖️

And against ImageIO

The Photoshop reader is judged by sips — macOS's own decoder, nothing to do with this code — pixel for pixel: exact on 2 073 600 pixels of a real file. ⛔ The first comparison blamed us for the instrument: At().RGBA() premultiplies, and the reference was already premultiplied, so it was done twice.

🧪

Mutation-tested

Deleting a guard and running the suite is the only way to know a test holds it. The PSD reader's sweep found a clamp nothing held — and the colour it protects is one Lab holds and sRGB cannot, which Go converts to a byte in an implementation-dependent way: 0 on one architecture, 251 on another.

🔄

s390x is big-endian and has a vector unit

So it is the one target where a byte-order assumption and a SIMD kernel can hide each other. Both are exercised: the scalar core and the vector kernel have to agree there as well as on amd64.

📏

32-bit targets are built, and that matters here

A picture's size is a number in a file: 300000 × 300000 overflows an int on a 32-bit build, and a bounds check that overflows waves the bomb through. The PSD reader multiplies as int64 before comparing, for that reason.

🧮

The scalar core is not a fallback

It is the reference. Every SIMD kernel is checked against it rather than against a recorded output, so an architecture with no kernel is slower and never different.

📚

Documentation of its own

The docs site is built with MkDocs and versioned with mike: the API reference, the roadmap, and the benchmark pages against scikit-image.

Pictures in, pictures out, with no C anywhere.

And where a picture becomes a document, go-pdfkit takes it from here — a PSD, a scan or a photograph onto a PDF page, in the same binary.
